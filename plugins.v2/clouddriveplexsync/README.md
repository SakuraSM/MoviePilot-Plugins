# TgToDrive Plex 增量同步

MoviePilot V2 插件。通过 TgToDrive OpenAPI 读取成功的整理记录，将目标目录映射为
Plex 容器路径，再提交该目录的局部扫描。插件只查询整理历史，不读取媒体内容，也不遍历网盘。

## 升级到 2.2.0

插件 ID、目录和配置前缀仍为 `CloudDrivePlexSync`、`clouddriveplexsync` 和
`clouddriveplexsync_`，现有安装可直接升级。

插件仅保留 TgToDrive OpenAPI → Plex：

- 移除 CloudDrive2 推送、目录刷新、拓扑查询和挂载点推导。
- 移除 Buffer 调整、恢复和播放状态检测。
- 移除 MoviePilot 入库事件、旧 Cookie 认证及相关配置、API。
- 保留直接路径映射、目录去重、跳过规则、扫描限速和手动补扫。
- 新增近期重叠回查、持久化去重账本、分批完整历史对账和执行中任务恢复。

已有 OpenAPI Token、直接路径映射、Plex 服务配置和去重账本继续使用。
仅新增模式按下面规则迁移游标和待扫描队列。只有 Cookie 的旧配置需要填写 OpenAPI Token；
依赖 CD2 MountPoint 的旧映射需要改为直接映射。

2.2.0 将历史处理改为“启用历史整理记录查询与扫描”开关，默认关闭。
旧配置显式选择 `include_history` 时沿用开启；存在新字段 `ttd_history_enabled` 时，以新字段的
`true` 或 `false` 为准。升级后的新增监听使用独立游标，历史开关不会重建新增基线。
从旧历史模式首次升级时，建立新增基线，并迁移历史对账断点与保留任务。

详情页提供“开启 / 继续历史处理”和“停止历史查询与扫描”按钮，操作即时生效并保存开关。
停止时取消等待中的历史查询，关闭历史任务入口和后续扫描提交，未完成任务持久化到保留队列。
再次开启后从历史断点继续处理。新增监听、手动补扫继续工作。
已经发出的 Plex 扫描请求无法撤回；中断时不能确认请求结果的任务也会保留，继续后可能再次提交。

同目录任务会合并，扫描按配置限速。默认不匹配 Plex 媒体库时保留并重试，旧配置显式选择
`skip` 时仍按该策略跳过。

## 前置条件

- MoviePilot V2 2.12.0 或更高版本。
- TgToDrive 已开启 OpenAPI，并创建有效 Token。
- MoviePilot 已配置并连接 Plex，Plex 版本至少为 1.20.0.3125。
- Plex 容器能够访问映射后的媒体目录。

插件不管理文件挂载。Plex 使用的挂载服务需要自行保持可用。

## 配置

在 TTD 的“实用工具 → OpenAPI”创建 Token，再填写插件配置：

```text
启用插件：开启
TgToDrive 地址：https://ttd.nings.top
TgToDrive API Token：你的 OpenAPI Token
TgToDrive 来源：光鸭云盘
Plex 服务：MoviePilot 中的 Plex 服务名
Plex 媒体库 ID：1,2（留空允许该服务的全部媒体库）
启用历史整理记录查询与扫描：关闭
TTD 目标根目录：/光鸭云盘/Media/Video/已整理
TTD 逻辑路径 → Plex 容器路径：
/光鸭云盘/Media/Video/已整理 => /data/CloudNas/Guangya
```

TTD 目标根目录填写云端逻辑路径。Plex 容器路径只填写在映射右侧。
多条映射按最长前缀匹配，并检查完整目录边界。目标越出根目录、包含 `..` 或无法匹配
Plex 媒体库时，不会退化为整库扫描。
Plex 报告运行平台为 Linux 时，媒体库路径开头的 `//` 会按 `/` 匹配；Windows 网络路径
保留原有的 `//服务器/共享` 形式。

Token 支持原始值、`Bearer ...` 和 `Authorization: Bearer ...` 三种形式。
插件只把 Token 放在 Authorization 请求头中，不写入 URL、状态页或运行日志。
TTD 的 OpenAPI 凭据拥有后台管理员权限，请使用 HTTPS 并妥善保存，需要时在 TTD 撤销。

地址可以是服务根地址，也可以是完整的 `/api/organize-history?...` 地址。
反向代理使用子路径时需要包含前缀，已有查询参数会被移除。

“跳过目录”支持相对于目标根目录的路径或完整逻辑路径，每行一条。
跳过目录和显式选择跳过的不匹配媒体库记录会记账，不再自动重试。
修改跳过规则不会自动重放已跳过记录，可通过手动补扫处理指定目录。

## 历史处理开关

| 开关 | 行为 |
|---|---|
| 关闭（默认） | 仅处理新增记录，不执行完整历史查询；停止后续历史扫描提交，保留历史断点和队列 |
| 开启 | 独立后台任务分批补查未登记的历史记录，恢复之前保留的历史扫描；新增监听继续运行 |

新增监听在首次成功查询时建立基线，不触发 Plex；普通重启沿用游标，继续处理停机期间
的新增记录。历史开关的开启、关闭和继续都不会重置这个基线。

新增监听不会把回查页中位于旧游标之后的未知记录当作新增内容。已在本轮基线之后接纳
的记录，其目标路径或事件时间变化时仍会重新处理，例如先进入临时目录，随后移入正式目录。
重启后保留这种记录资格和去重账本。启用前的旧记录、仅在游标之后晚成功的未知记录，
需要开启历史处理才能补查。历史关闭时调用历史对账 API 会返回明确错误。

历史任务使用独立来源 `ttd_history`，新增任务使用 `ttd`。同目录和父子目录只在同类队列中
合并，历史父目录不会吸收新增子目录。关闭历史后，新增子目录仍按自己的准确目录扫描。
详情页和运行日志会显示开启、停止、断点、保留任务数量与当前查询状态。

这里的“仅新增”控制哪些 TTD 记录触发扫描请求。Plex 对目标目录的局部扫描仍可能检查
其中已有文件；插件不会修改 Plex 的分析选项或 CD2 挂载配置，也不会取消 Plex 中其它扫描任务。

## 资源洗版与手动补扫

“仅新增”指新增 TTD 整理记录，不要求影片或剧集此前不存在。洗版成功后如果 TTD 产生新的
成功记录，即使目标目录不变，插件也会重新提交该目录的 Plex 扫描。仅在网盘原地替换文件而
没有新的整理记录，或者既有记录的 ID、路径和事件时间等去重字段没有变化时，插件无法主动感知。

需要人工补偿时，在插件设置的“手动刷新媒体库目录”输入 Plex 容器内的绝对目录路径，点击
“刷新指定目录”即可入队，无需保存配置或重启插件。例如：

```text
/data/CloudNas/Guangya/动漫/国产动漫/剧集名称/Season 1
```

该路径直接匹配所选 Plex 媒体库，不要求存在 TTD 路径映射，也不受 TTD 跳过目录规则影响。
路径必须位于允许的媒体库内；输入媒体库根目录会扫描该根目录。手动任务不等待同目录合并
时间，仍遵守扫描提交限速和失败重试规则。页面提示“已加入扫描队列”不表示 Plex 已完成索引。

自动和手动操作都是 Plex 目录扫描，目的是让 Plex 检查媒体文件变化；不会强制刷新既有影片的
海报、简介等元数据。Plex 是否识别替换还取决于挂载目录是否及时显示新文件和 Plex 的索引状态。

## 防漏与恢复

插件请求 `GET /api/organize-history`，传入 `source`、`page`、`limit` 和 `status=success`。
默认配置如下：

| 配置 | 默认值 | 行为 |
|---|---:|---|
| 启用历史整理记录查询与扫描 | 关闭 | 启用前历史不触发 Plex，可随时停止或继续 |
| 轮询间隔 | 30 秒 | 快速发现新增成功记录 |
| 每页记录数 | 100 | 单页查询量 |
| 快轮询最大页数 | 5 | 限制单轮请求量 |
| 遇到旧记录后继续回查 | 2 页 | 检查已接纳新增记录的版本变化 |
| 完整历史对账间隔 | 6 小时 | 仅历史模式启用，从上一次对账完成时计算 |
| 完整历史对账批量 | 每轮最多 2 页 | 仅历史开关开启时启用，独立任务按轮询间隔执行，断点续跑 |
| 同目录合并等待 | 30 秒 | 合并重复扫描请求 |
| 每秒提交扫描数 | 1 | 限制 Plex 请求速率 |
| 扫描队列容量 | 10,000 | 容量不足时保留整理记录重试 |

通常无新记录时，快轮询读取 3 页。仅历史模式的对账进行中每轮再读取最多 2 页。
增加回查窗口或缩短轮询间隔会增加 TTD 查询量，不会增加网盘目录遍历。

处理记录后，将记录 ID、目标路径、事件时间和状态对应的版本保存到插件数据目录中的
`history.sqlite3`。账本不受最近 1,000 个游标 ID 的限制，也保存仅新增模式下已接纳的记录。
仅新增模式只处理本轮基线后接纳记录的新版本，历史模式处理所有未登记版本。

快轮询遇到已处理 ID 后仍检查当前页，并继续回查配置的页数。仅新增模式未找到旧游标时
停止提交并报告缺口；下一次重试会临时扩大到每页 100 条、最多 20 页。找到原游标后才提交其前面的新增
记录，不会自动回放历史或重建基线。如果仍未找到，插件继续暂停推进，按 1、5、15、30、60 分钟
逐步退避；旧记录被清理或缺口超过 2,000 条时，需要人工确认处理方式。开启历史处理后，独立任务会分批对账，补查窗口之外
晚成功的记录，不会把当前窗口视为已经补齐全部历史。

新增监听和历史处理共享去重账本，但会区分仅由历史任务接收的记录。即使先由历史任务接收，
之后新增监听发现同一记录时也会独立接收，避免关闭历史处理后新增任务留在保留队列。升级前
账本中已登记记录的来源无法追溯；如需补扫此前遗漏的目录，可使用手动补扫。

对账每处理完一页才保存下一页页码；提交失败时停留在当前页。重启后从已保存的位置继续。
队列接受任务并持久化后，才将整理记录记入账本。账本写入前中断可能导致重复提交，目录
队列会在各自来源范围内合并重复任务。

扫描任务执行前会持久化为 `inflight`。Plex 接受局部扫描请求后，任务才从队列移除。
重启时 `queued` 和 `inflight` 都恢复为待执行任务。扫描期间同目录出现的新变化会保留为
下一次扫描任务。单个目录失败不会阻塞其它目录。
旧队列格式无效或恢复任务超过配置容量时，插件拒绝启动并报告原因，不会静默丢弃任务。

这里保证的是扫描请求可重试，Plex 接受请求不等于媒体索引已经完成。
服务端当前提供页码分页，未提供快照或稳定增量事件游标。对账期间数据可能变化，因此
不能承诺任意并发修改下绝对不漏；记录在服务端保留足够时间、接口可用且任务最终成功时，
历史模式的周期对账会持续补查。仅新增模式主动关闭了完整历史补漏。
源记录在查询前被删除或清理后，插件无法恢复其内容。

`401/403` 和登录重定向按 5、15、30、60 分钟退避；网络错误按 5、15、30、60 秒退避。
恢复期间保留游标、账本和待扫描队列。

## 扫描日志

扫描日志同时写入 MoviePilot 运行日志和插件的“最近处理记录”，包含以下阶段：

| 阶段 | 含义 |
|---|---|
| `QUEUE` | 目录已入队并完成队列持久化 |
| `SCAN_START` | 已重新匹配 Plex 媒体库，准备调用局部刷新接口 |
| `SCAN_SUBMITTED` | Plex 局部刷新请求已成功返回 |

每条日志包含 `source`、`ttd_path`、`plex_path`、`section_id`、`section_title` 和
`section_root`，分别表示来源、TTD 逻辑目录、Plex 容器目录、媒体库 ID、名称和命中的根目录。

`QUEUE` 额外打印 `queued_plex_path`。子目录任务合并到已有父目录任务时，`plex_path`
是本次请求的映射路径，`queued_plex_path` 是实际排队的父目录。
`SCAN_START` 和 `SCAN_SUBMITTED` 使用执行时重新匹配的路径和媒体库信息，可能与入队时
不同。字段使用 JSON 编码，目录名中的换行不会拆成多条日志。

`SCAN_SUBMITTED` 表示请求提交成功，不表示 Plex 已完成媒体索引。

详情页将运行日志、等待确认和“Plex 已确认收录”的内容分开展示，每页 5 条，支持翻页和
手动刷新。日志保留最近 2,000 条；已确认记录最多保留 10,000 条，页面显示最近 2,000 条。
记录保存在插件数据目录的 `activity.sqlite3` 中，普通重启后仍可查看；不会回填升级前的记录。

对 TTD 成功记录中包含文件名、媒体名及季集信息的扫描，Plex 接受目录扫描后会在后台核验。
插件按媒体名查找 Plex 条目，并比对 Plex 返回的具体文件路径；只有找到相同路径且 Plex 没有
明确报告该文件不可用时，才显示“Plex 已确认收录”。首次核验最早在请求提交 15 秒后进行，
核验任务串行执行，最多每秒检查一条；未找到或 Plex 暂不可用时按 30 秒至 1 小时退避重试。
缺少文件名的记录会在日志中说明无法核验；缺少媒体名或季集编号的记录保留在待确认列表。
Plex 不支持所需筛选字段、媒体名称不匹配或返回的路径与映射路径不一致时，也会保持待确认，
不能据此判定入库失败。

确认记录表示 Plex 当时收录了这个路径，不表示元数据抓取已经完成。同名文件原地覆盖时，
仅凭路径不能证明 Plex 已更新为新版本。手动目录扫描不包含具体文件列表，因此只显示扫描
请求日志，不会凭目录中已有文件推断哪些内容由该次扫描入库。时间按 MoviePilot 主机时区显示。

## 插件 API

所有接口需要 MoviePilot Bearer 认证，插件 ID 仍为 `CloudDrivePlexSync`：

- `GET /api/v1/plugin/CloudDrivePlexSync/status`：查询认证、队列、对账进度和最近记录。
- `POST /api/v1/plugin/CloudDrivePlexSync/test`：验证 TTD 历史查询与 Plex 连接。
- `POST /api/v1/plugin/CloudDrivePlexSync/flush`：立即处理当前待扫描目录。
- `POST /api/v1/plugin/CloudDrivePlexSync/resync`：手动提交一个准确目录。
- `POST /api/v1/plugin/CloudDrivePlexSync/resync/plex`：直接提交 Plex 容器目录。
- `POST /api/v1/plugin/CloudDrivePlexSync/reconcile`：历史开启时取消当前历史查询，从第一页重新启动对账；历史关闭时拒绝处理。
- `POST /api/v1/plugin/CloudDrivePlexSync/history/start`：即时开启 / 继续历史查询和扫描，保存开关为 `true`。
- `POST /api/v1/plugin/CloudDrivePlexSync/history/stop`：即时停止历史查询与后续扫描提交，保存开关为 `false`。

手动补扫请求示例：

```json
{
  "cloud_path": "/光鸭云盘/Media/Video/已整理/电影/片名"
}
```

直接指定 Plex 目录时，请求体为：

```json
{
  "plex_path": "/data/CloudNas/Guangya/电影/片名"
}
```

新版本会在队列中保存直接 Plex 路径及其类型。降级至旧版本前，应先处理完这类未完成的手动
任务；旧版本无法识别该队列格式。

状态中的 `ttd` 是新增监听状态，其 `audit_next_page` 始终为 0。
`ttd.baseline_at` 是新增基线建立时间；`ttd.history_gap` 表示新增回查未找到旧游标。
`history_processing` 独立显示历史开关 `enabled`、任务运行 `running`、查询中
`query_in_progress`、下一页 `next_page` 和历史错误 `last_error`。
历史 `next_page=0` 表示本轮对账完成，其它值为下一页页码；关闭不会清空历史断点。
`history_mode` 保留为兼容字段，历史开启时为 `include_history`，关闭时为 `new_only`。
`held_history_scans` 是保留而未继续提交的历史任务数量；`inflight_scans` 是当前提交中的任务数量。

## 开发验证

核心测试使用临时 SQLite、模拟 HTTP 与 Plex，不会修改真实媒体库：

```bash
python3 -m unittest discover -s tests -v
python3 -m compileall -q plugins.v2/clouddriveplexsync
```

升级并打开新版本页面后，可运行无障碍检查脚本：

```bash
bash ~/.agents/skills/deterministic-frontend/scripts/a11y-audit.sh '<MoviePilot 插件详情页 URL>'
```

本地测试不代表 MoviePilot 页面已部署或通过在线交互验证。

仓库中的 `.env` 和 `.env.*` 只用于本地验证，并已加入 Git 忽略规则。
插件运行时使用 MoviePilot 配置页的 Token，不自动读取开发目录中的凭据文件。
